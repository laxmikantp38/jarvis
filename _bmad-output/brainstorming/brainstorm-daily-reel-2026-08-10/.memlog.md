- (decision by user) REQUIREMENT #1 LOCKED: build a Jarvis-style application that (a) proactively reminds him time-to-time of anything pending from his side, and (b) executes work on demand when he asks.
- (decision by user) Reminders must be PROACTIVE and time-anchored to his real routine, delivered over WhatsApp - e.g. wake call at 6:00/6:30, gym nudge at 7:30, leave-gym nudge at 9:10. Jarvis reaches out to him; he does not have to open an app.
- (insight by coach) CONSTRAINT to resolve in design: programmatic WhatsApp VOICE calls are not available via the WhatsApp Business API - only messages (text/template/voice-note). A real ringing wake-up needs a phone call via Twilio/Exotel, or a WhatsApp message plus a PSTN call. Decide channel per nudge: message for soft nudges, actual call for wake-up.
- (decision) Scope of requirement #1 refined from 'Daily Planner' to 'Proactive Reminder + On-demand Doer' - the planner is implied (it needs the schedule and the pending-work list) but the felt value is Jarvis reaching OUT, not him checking in.
- (insight by coach) SYNTHESIS: the through-line of the session is that Jarvis must reach OUT, not wait to be opened. Every candidate that scored high (wake call, gym nudge, pending-work reminder, reel deadline) is the same shape - a scheduled, channel-delivered nudge tied to his fixed routine. The 'do work when asked' half is the second shape. So requirement #1 is really two primitives: a SCHEDULER+NOTIFIER and a TASK EXECUTOR, sharing one memory of his routine and pending work. Everything later (Railzy briefings, reel pipeline, commute voice) is a new nudge type or a new tool on those same two primitives.
- (decision) Non-negotiables carried into build: name must be swappable (user-owned), LLMProvider abstraction for model independence, per-tool permissions, audit logging - per the PDF product philosophy and the operating principle to define scope first and build incrementally.
- (decision by user) Artifact chosen: intent doc only (brainstorm-intent.md). User goes straight to PRD next.
- (idea by user) UI REQUIREMENT: the interface should look and feel like Jarvis (Iron Man style). The agent section specifically should be rendered as an OFFICE WITH EMPLOYEES - each specialized agent is an employee, and Jarvis is the boss driving/directing all of them.
- (insight by coach) CONNECTION: the office metaphor is not just decoration - it is the observability requirement from the PDF made visible. Each employee card can surface live status, current task, elapsed time, token/cost, and pending approvals. Delegation stops being hidden in logs and becomes the main screen.
- (insight by coach) BUILD-VS-ADOPT: OpenClaw (github.com/openclaw/openclaw, MIT, self-hosted Node gateway) already implements most of requirement #1 - WhatsApp/Telegram/Signal channels, cron + proactive morning briefings, persistent memory, skills system for on-demand tasks. Composio ships a hardened fork (secure-openclaw). Gap = the Jarvis HUD UI and the office-of-employees agent view, which are his to build.
- (question) OPEN DECISION for PRD: adopt OpenClaw as the engine and build the Jarvis UI on top, or build the scheduler/notifier/executor from scratch in FastAPI as originally planned? Adopting saves months but makes the backend Node, not Python/FastAPI. Also note WhatsApp bridges are typically unofficial (ban risk) and still cannot place voice calls.
- (insight by coach) EVALUATED isair/jarvis (1.6k stars, Python, Ollama/Whisper/Piper, MCP tools, strong self-organising memory). VERDICT: does NOT fit requirement #1. It is a LOCAL DESKTOP VOICE assistant - no WhatsApp or messaging channel, no cron/scheduled proactive reminders, no web dashboard, macOS-primary with Windows lagging, needs a local GPU, and dual-licensed (commercial use requires contacting the authors - a problem under Naxova). Fatal mismatch: it is pull-based and only runs when his PC is on, but requirement #1 needs an always-on server that pushes a 6 AM wake-up while he is asleep.
- (insight by coach) isair/jarvis is still worth revisiting later for V3 (local computer agent) and for its memory design (auto-splitting by topic, knowledge graph, redaction before storage) - good reference architecture even if not adopted.
- (insight by coach) COST: OpenClaw itself is FREE - MIT licensed (OpenClaw Foundation), commercial use permitted, no paid tier or mandatory cloud subscription, and it supports local model providers. Real costs sit elsewhere: LLM API usage (or a local model), hosting for the always-on gateway (his existing AWS EC2 can carry it), WhatsApp channel (unofficial bridge free but ban risk vs paid official Business API per-conversation), and per-call charges if Twilio/Exotel is used for the 6 AM ringing wake-up.
- (insight by coach) DATA RISKS identified (apply whether adopting OpenClaw or building own): 1) Unofficial WhatsApp bridge links his PERSONAL number via a WhatsApp Web session - ban risk on his primary comms, and session credentials on the server mean a breach lets an attacker message as him. 2) Employer/client confidentiality - piping Gate6 or personal-client work through a third-party LLM API may breach NDA or employment terms. 3) Always-on internet-facing gateway holding chat history, OAuth tokens (GitHub/Gmail/Calendar) and tool access - compromise means the attacker can ACT as him. 4) Prompt injection via web/email content the agent reads. 5) Supply chain - community skills/plugins in a fast-growing project are unvetted code. 6) The memory store concentrates his whole life (routine, family, finances, clients) into one breachable place.
- (decision) MITIGATIONS to carry into the PRD: dedicated WhatsApp number (never the personal one); hard rule that employer/client confidential data never leaves to a hosted model (local model or exclusion rules); gateway not exposed to the public internet (VPN/Tailscale, no open ports); secrets in a manager not env files; per-tool permissions plus approval on risky actions; audit logging; pinned dependencies and vetted skills only; encryption at rest for the memory store.
- (decision by user) DECISION: BUILD THE ENGINE. Not adopting OpenClaw as a dependency. Own the scheduler/notifier/executor in his own stack (Python/FastAPI as originally planned). OpenClaw and isair/jarvis remain reference architectures to study, not dependencies.
- (idea by user) ARCHITECTURE PROPOSAL: do not deploy everything on a server. Jarvis runs LOCALLY, launches on system startup, and accepts commands via WhatsApp, Telegram, or a Jarvis web UI.
- (insight by coach) ASSESSMENT of local-only: the RECEIVE half works fine behind home NAT (Telegram long-polling and the WhatsApp Web bridge are both outbound connections, no port forwarding or public IP needed). The PUSH half breaks - his PC is off at 6 AM, and he is away from it during gym, commute and office, which is exactly when the nudges are due. Local-only reproduces the same fatal flaw that disqualified isair/jarvis.
- (decision by coach) RECOMMENDED: HYBRID, which is what the source brief already described (cloud component + local computer agent). Cloud side stays tiny - scheduler, notifier, channel gateway - holding minimal data, so it is cheap and low-risk. Local side is the executor for anything touching his files, code or private data, and dials OUT to the cloud so no inbound ports are exposed. When the PC is off, nudges still fire from cloud and execution tasks queue until the local agent reconnects.
- (decision by user) MVP ARCHITECTURE LOCKED: local-first. Jarvis runs on his own machine, launches on system startup, accepts commands via WhatsApp, Telegram, or a local Jarvis web UI. Cloud is deferred - will expand later.
- (insight by coach) Accepted trade for MVP: scheduled nudges only fire while the PC is running, so the 6 AM wake-up requires leaving the machine on overnight - otherwise that one feature slips to phase 2. In exchange, local-only removes the two top data risks entirely (no employer/client data to a hosted model, no internet-facing gateway holding OAuth tokens).
- (decision) DESIGN GUARDRAIL for the clean expansion path: put the notifier behind an interface from day one so the delivery channel (WhatsApp / Telegram / PSTN call) and the host (local / cloud) can each be swapped without touching the scheduler or executor. Phase 2 then lifts only the scheduler+notifier to a small cloud box, with the local agent dialling OUT to it - no inbound ports, no rewrite.
- (decision by user) MVP SCOPE CONFIRMED: local only. On system start it launches automatically and greets him with a welcome message.
- (decision by user) HARD NAMING RULE: the word JARVIS must NEVER appear in code. It may appear in user-facing MESSAGES only, sourced from configuration, because the assistant will be renamed later. Renaming must be a single config change with zero code edits.
- (decision by coach) NAMING RULE made concrete: one config key ASSISTANT_NAME (default 'Jarvis') is the single source of truth. Code uses neutral identifiers everywhere - agent, assistant, core - in module names, class names, package names, DB tables, API routes, log channels and env var prefixes (AGENT_ not JARVIS_). All user-facing strings interpolate the config value. Acceptance test: grep -ri jarvis over the source tree returns zero hits outside config defaults and message templates.
